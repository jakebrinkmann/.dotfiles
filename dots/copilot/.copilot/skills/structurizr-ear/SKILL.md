# Skill: Structurizr EAR Best Practices

## 1. `!identifiers hierarchical` — Inheritance and View Path Rules

### Parent propagates to child

When the **parent** EAR workspace declares `!identifiers hierarchical`, ALL
elements in the child workspace (including `!include`d fragments) also receive
hierarchical identifiers. You **cannot** suppress this in the child.

hgrail's `aggregate_workspace.py` detects this flag and generates component view
targets using the `sys.container` dot-notation path automatically.

### Component views in `workspace extends` workspaces

Because the parent (`ear-target.dsl`) uses `!identifiers hierarchical`, every
component view inside `workspace.dsl` **must** use the hierarchical path:

```dsl
// ✅ CORRECT — hierarchical path (sys_ident.container_ident)
component dealerPortalDraftBilling.atfDraftEngine "L3_atfDraftEngine" { include * }

// ❌ WRONG — flat identifier fails when parent has !identifiers hierarchical
component atfDraftEngine "L3_atfDraftEngine" { include * }
```

### Never add `!identifiers hierarchical` to the child workspace itself

The child (`workspace extends "..."`) must NOT re-declare `!identifiers
hierarchical`. The parent's declaration already propagates. Adding it in the
child again causes duplicate-identifier errors or unexpected scoping issues.

### Container views: skip external stubs

Do NOT generate a `container <id>` view for a softwareSystem that has no child
containers (e.g., an `Existing External` stub). The `aggregate_workspace.py`
aggregator enforces this automatically.

## 1a. `!element` — Identifier Rules (CRITICAL)

`!element` takes a DSL **identifier** — never a quoted display name:

```dsl
// ✅ CORRECT — bare identifier
!element eformsV2 { tags "tenant-isolation-required" }

// ❌ WRONG — quoted display name causes: "An element identified by '...' could not be found"
!element "eForms v2" { tags "tenant-isolation-required" }
```

**How to find the correct identifier**: `extract_ear_data.py` outputs
`ear_data.ear_systems: [{id, name}]`. The `id` field is the DSL identifier.
Use it in both `!element` and relationship lines:

```dsl
mySystem -> eformsV2 "submits form data to"   // ← use identifier
```

**`!ref` has been removed** from Structurizr DSL. Use `!element` instead.

### External stubs for systems absent from the EAR DSL snapshot

If a system exists in the compiled `workspace.json` but NOT in the EAR `.dsl`
source files, you cannot use `!element` to reference it. Define it as a new
softwareSystem in the epic fragment:

```dsl
// System exists in workspace.json but not in DSL source — define a stub:
nfaTransferApplications = softwareSystem "NFA Transfer Applications" \
    "External system for NFA transfers." {
  tags "Existing External"
}
// Then reference using the stub identifier:
myContainer -> nfaTransferApplications "submits ATF Form 4"
```

### `workspace.json` is NOT a source of truth for DSL identifiers

`workspace.json` is a **compiled artifact** generated by `structurizr/structurizr`.
The `"structurizr.dsl.identifier"` values in that JSON reflect the hierarchical
compiled state, not the flat DSL identifiers. Never use `workspace.json` to look
up identifiers for `!element` or relationship lines. Use the `.dsl` source files.

## 2. Context Fragment Structure

`domains/*/context.dsl` files (and `src/domain/*/context.dsl`) are **pure fragments** — no `workspace`, `model`, or `views` wrappers:

```dsl
# context.dsl — fragment only
mySystem = softwareSystem "My System" {
    manager = container "Manager" {
        tags "Manager"
        ...
    }
    engine = container "Engine" {
        tags "Engine"
        ...
    }
    resourceAccess = container "Resource Access" {
        tags "ResourceAccess"
        ...
    }
}
```

The aggregator (`workspace.dsl` or `enterprise-landscape.dsl`) wraps every fragment with `softwareSystem { !include domains/*/context.dsl }`.

**DSL scope rules (critical):**
- `softwareSystem` and `person` declarations must be inside `model {}`.
- Content placed between `model`'s closing `}` and `views {` is workspace scope — placing model elements there is a compile error.
- `views {` is **not** a safe anchor for injecting model content.

## 3. `workspace extends` for Specs / Overlay Workspaces

Specs and target-state overlays must use `workspace extends`, not `!include` coupling into the base workspace.

### Syntax

```dsl
# local file
workspace extends ../../model-as-is/workspace.dsl {
    ...
}

# or remote HTTPS URL
workspace extends https://example.com/base/workspace.dsl {
    ...
}
```

**All identifiers from the parent workspace are available automatically** — no re-declaration needed. If the base workspace defines `mySystem`, the child can reference it directly.

### Typical specs-to-be pattern

```dsl
# specs-to-be/<initiative>/workspace.dsl
workspace extends ../../model-as-is/workspace.dsl {
    model {
        !element mySystem {
            # Add new containers to an existing system
            newService = container "New Service" { tags "Engine" "Service" "New Internal" }
            newService -> mySystem.existingDb "Reads from"
        }

        # Add cross-system relationships
        mySystem -> otherSystem "Integrates with via new API"
    }

    views {
        container mySystem "L2_MySystem_ToBe" "Target state" {
            include *
            autoLayout
        }
        !include dynamic-views.dsl
    }
}
```

### `!element` — extend an existing element

```dsl
!element <identifier> {
    # add containers, components, tags, properties, relationships
}
```

For JSON-based workspaces, find by canonical name and assign an identifier:

```dsl
myAlias = !element "Software System/Container Name" {
    tags "New Tag"
}
```

### `!relationship` — extend an existing relationship

```dsl
rel = mySystem -> otherSystem "Calls"

# later, or in a child workspace:
!relationship rel {
    tags "In Progress"
    properties { "adoEpic" "1234" }
}
```

### `!elements` / `!relationships` — bulk operations via expressions

Tag or annotate a set of elements/relationships matching an expression:

```dsl
!elements "element.tag==Legacy" {
    tags "Decommission"
    properties { "decommissionBy" "2026-Q4" }
}

!relationships "relationship.tag==Async" {
    tags "Review"
}
```

### Deprecation warning — `!ref` / `!extend` REMOVED

> ⛔ **`!ref` and `!extend` have been removed from Structurizr DSL.**
> They were first deprecated, and are now a **compile error**.
> Any DSL containing `!ref` or `!extend` will fail validation with:
> `!ref was previously deprecated, and has now been removed - please use !element or !relationship instead`
>
> **Migration (required, not optional):**
> | Old (removed) | New (use this) |
> |---|---|
> | `!ref "Name" { … }` | `!element "Name" { … }` |
> | `!extend identifier { … }` | `!element identifier { … }` |
> | `!ref identifier { … }` | `!element identifier { … }` |
>
> `!element` accepts both a quoted display name string (for elements without an in-scope identifier)
> and a bare identifier. It is **never** valid on a relationship line — use string display names there.

### Rules

- Each spec workspace is self-contained and can be validated independently.
- The base `model-as-is` workspace **must not** `!include` files from `specs-to-be/` — one-way dependency only.
- `workspace extends <file>` makes the DSL **non-portable** (the `structurizr.dsl` workspace property is not embedded). This is expected for EAR multi-workspace setups.

## 4. MERA Container Topology

Every container must carry exactly one MERA tag: `Manager`, `Engine`, or `ResourceAccess`.

| Tag | Role |
|-----|------|
| `Manager` | Orchestration — routes, sessions, HTTP surfaces |
| `Engine` | Pure domain logic — state machines, business rules |
| `ResourceAccess` | ACL adapters — database, external APIs, Key Vault |

This is a hard Gate 0 policy. Containers without a MERA tag fail validation.

### F# Quarantine Rule (P5)

**F# exists only in `domain.fs` — it is never deployed to production.**

The `technology` field of every `container` must reflect the actual production runtime:

```dsl
// ✅ CORRECT — production runtimes
container "Access Gateway API" "..." "C# / ASP.NET Core Minimal API" { ... }
container "LaunchSession Engine" "..." "C# / .NET 10" { ... }
container "Dealer Portal Web App" "..." "React / TypeScript" { ... }

// ❌ WRONG — F# is the modelling language, not the deployed runtime
container "LaunchSession Engine" "..." "F# / .NET 10" { ... }
container "Access Gateway API" "..." "F# / ASP.NET Core Minimal API" { ... }
```

Components (L3, inside Engine containers) may describe their design pattern in the technology field:

```dsl
component "LaunchSession" "Event-sourced aggregate root." "C# / Domain Model" { ... }
```

`domain.fs` uses F# as a mathematical modelling tool in the EAR repo. It has no production deployment footprint.

## 5. View Naming Conventions

### C4 Level → DSL view type → key prefix

| C4 Level | Meaning | DSL keyword | Key prefix |
|----------|---------|-------------|------------|
| **L0** | Enterprise Landscape | `systemLandscape` | `L1_` |
| **L1** | System Context | `systemContext <system>` | `L1_` |
| **L2** | Container View | `container <system>` | `L2_` |
| **L3** | Component View | `component <container>` | `L3_` |
| **L2D** | Dynamic — container scope | `dynamic <system>` | `L2D_Epic{N}_` |
| **L3D** | Dynamic — component scope | `dynamic <container>` | `L3D_Epic{N}_Feature{N}_` |
| **DEP** | Deployment | `deployment <system> <env>` | `DEP_` |

All views must use explicit keys (see section 14). Always include `autoLayout`.

### `systemLandscape` — no element parameter

`systemLandscape` takes **no element parameter** (unlike every other view type). It renders all people and software systems in the entire workspace:

```dsl
views {
    // L0 — enterprise overview
    systemLandscape "L1_Enterprise" "All SC software systems and external actors" {
        include *
        autoLayout
    }

    // L1 — single system in context
    systemContext mySystem "L1_MySystem_Context" {
        include *
        autoLayout
    }

    // L2 — containers inside a system
    container mySystem "L2_MySystem_Containers" {
        include *
        autoLayout
    }
}
```

| View type | Syntax | What `include *` renders |
|-----------|--------|--------------------------|
| `systemLandscape` | `systemLandscape [key] [desc]` | All people + all softwareSystems |
| `systemContext` | `systemContext <system> [key] [desc]` | The system + its direct neighbours |
| `container` | `container <system> [key] [desc]` | All containers in the system + neighbours |
| `component` | `component <container> [key] [desc]` | All components in the container + neighbours |
| `deployment` | `deployment <*\|system> <env> [key] [desc]` | All deployment nodes in that environment |

## 6. Tag Dimensions and Styles

Elements carry tags across **three independent dimensions** — an element commonly has one tag from each:

| Dimension | Tags | Controls | Mandatory? |
|-----------|------|----------|------------|
| **Lifecycle** | `"New Internal"`, `"New External"`, `"Existing Internal"`, `"Existing External"`, `"Legacy"`, `"In Progress"` | Color + border style | ✅ Every element |
| **MERA role** | `"Manager"`, `"Engine"`, `"ResourceAccess"` | Gate 0 enforcement only | ✅ Every container |
| **Technology shape** | `"Infrastructure"`, `"Person"` (and aspirational: `"Frontend"`, `"Gateway"`, `"Service"`, `"Queue"`) | Shape + background override | ⚠ Only when shape differs from default box |

Example element with all three dimensions:
```dsl
container "Partners API" "Orchestrates inbound partner data flows." "F# / ASP.NET Core" {
    tags "Manager" "Existing Internal"
}

container "Entitlement Store" "Authoritative store for dealer entitlement records." "Azure SQL" {
    tags "ResourceAccess" "Infrastructure" "Existing Internal"
}
```

### Lifecycle tag decision flowchart

```
Is the element SC-owned / built in-house?
├── YES → Internal
│         Is it live in production?
│         ├── YES → "Existing Internal"   (dark red #A80007, solid RoundedBox)
│         ├── NO, active epic → "New Internal"   (green #2e8b57, dashed border)
│         └── Being decommissioned → "Legacy"   (black #000000, dashed border)
└── NO  → External (3rd-party API, SaaS, partner system)
          Is it already integrated/live?
          ├── YES → "Existing External"   (charcoal #555555, solid RoundedBox)
          └── NO, planned → "New External"   (teal #008b8b, dashed border)

Is this a *relationship* (not an element) that isn't built yet?
└── Tag the relationship "In Progress"   (dashed green line #00aa44)
```

**`"In Progress"` on elements** — use when the element itself is BARD-specified but has no active epic yet. If there *is* an active epic, use `"New Internal"` instead.

**`"New Internal"` vs `"In Progress"` on elements:**
- `"New Internal"` = has a sprint / ADO epic — work is scheduled
- `"In Progress"` = architectural intent declared, work not yet scheduled

### Technology shape tags — only two are styled in the canonical block

| Tag | Shape | Use when |
|-----|-------|----------|
| `"Infrastructure"` | Cylinder, `#4a4a6a` dark purple | Databases, caches, queues, storage (any data-at-rest container) |
| `"Person"` | Person stick figure, `#ffcc00` DDD yellow | Human actors — OR a softwareSystem that *represents* a user/browser (e.g., a React SPA acting as the human entry point) |

The remaining technology tags (`"Frontend"`, `"Gateway"`, `"Service"`, `"Queue"`) are aspirational — they have **no style defined** and produce no visual effect until added to the `styles {}` block. Do not use them unless you add the corresponding style.

### The "Person tag on a softwareSystem" pattern

A React SPA or browser-rendered UI is modelled as a `softwareSystem` (it has a URL, it's independently deployed) but tagged `"Person"` to render as a stick figure at L0/L1 where it represents the human entry point:

```dsl
customerBrowser = softwareSystem "Customer Browser" "Authenticated SC.com storefront session." {
    tags "Existing External" "Person"
}
```

At L2+ (container/component views) the same element renders as a box — the Person shape only applies at L0/L1 where actor vs system distinction matters.

### Never use brand colors

Lifecycle tags encode semantic meaning using fixed EAR colors. **Never override with brand-specific colors** (Magento red, NetSuite grey, Sezzle teal, etc.). If a diagram reader needs to know which vendor a system is, that's what the `technology` field and element name are for — not the background color.

```dsl
// ❌ WRONG — mixes brand identity into lifecycle semantics
element "Magento" { background #e22d00 }

// ✅ CORRECT — Magento is an Existing External; color communicates lifecycle
element "Existing External" { background #555555; shape RoundedBox }
```

**Lifecycle tag meanings:**

| Tag | Color | `border` | Meaning |
|-----|-------|----------|---------|
| `"New Internal"` | `#2e8b57` green | `dashed` | SC-owned, scheduled (active epic) |
| `"New External"` | `#008b8b` teal | `dashed` | Third-party integration in-flight |
| `"Existing Internal"` | `#A80007` dark red | solid | SC-owned, live in production |
| `"Existing External"` | `#555555` charcoal | solid | Third-party, already integrated |
| `"Legacy"` | `#000000` black | `dashed` | Deprecated / actively decommissioning |
| `"In Progress"` | `#2e8b57` green | `dashed` | Architectural intent, no epic yet |

**Relationships** also support the `"In Progress"` tag to show planned integrations as dashed lines.

### Canonical EAR `styles {}` block

Place this in the `views {}` section of `workspace.dsl` (not in fragments):

```dsl
styles {
    // ── Actors ────────────────────────────────────────────────────────
    element "Person" {
        shape Person
        background #ffcc00
        color #ffffff
    }

    // ── Lifecycle Boundaries ──────────────────────────────────────────
    element "New Internal" {
        background #2e8b57
        color #ffffff
        border dashed
    }

    element "New External" {
        background #008b8b
        color #ffffff
        border dashed
    }

    element "Existing Internal" {
        shape RoundedBox
        background #A80007
        color #ffffff
    }

    element "Existing External" {
        shape RoundedBox
        background #555555
        color #ffffff
    }

    element "Legacy" {
        background #000000
        color #ffffff
        border dashed
    }

    element "Infrastructure" {
        shape Cylinder
        background #4a4a6a
        color #ffffff
    }

    // ── In-Progress (BARD-specified, not yet implemented) ─────────────
    element "In Progress" {
        background #2e8b57
        color #ffffff
        border dashed
    }

    relationship "In Progress" {
        style dashed
        color #00aa44
    }

    // ── C4 Internal Architecture ──────────────────────────────────────
    element "Container" {
        background #438dd5
        color #ffffff
    }

    element "Component" {
        background #85bbf0
        color #000000
    }
}
theme default
```

### Element style properties

```dsl
element <tag> {
    shape   <Box|RoundedBox|Circle|Ellipse|Hexagon|Diamond|Cylinder|Pipe|Person|WebBrowser|...>
    background  <#rrggbb|color name>
    color       <#rrggbb|color name>
    stroke      <#rrggbb|color name>
    strokeWidth <1-10>
    border  <solid|dashed|dotted>
    opacity <0-100>
    fontSize <integer>
}
```

### Relationship style properties

```dsl
relationship <tag> {
    style   <solid|dashed|dotted>   # preferred; 'dashed true' is legacy alias
    color   <#rrggbb|color name>
    thickness <integer>
    routing <Direct|Orthogonal|Curved>
    fontSize <integer>
    opacity <0-100>
}
```

`theme default` must go **after** the closing `}` of `styles {}` — not inside it.

## 8. Description and Label Strictness (Policy 7 / DFD Anti-Pattern)

**Hard limits enforced by Gate 0:**
- Element descriptions (softwareSystem, container, component): **≤ 80 characters**
- Relationship labels: **≤ 60 characters**

### What goes in a description

A description is **one responsibility sentence** — what the element does, not how it does it.

```dsl
// ✅ CORRECT — concise responsibility
launchSessionAggregate = component "LaunchSession" 
    "Event-sourced aggregate root governing session auth and launch token lifecycle." 
    "F# Discriminated Union"

// ❌ WRONG — DFD anti-pattern, floods the diagram box
launchSessionAggregate = component "LaunchSession" 
    "Aggregate root. States: Unauthenticated → PortalSessionValidated → EntitlementChecked → LaunchTokenActive | Denied | Expired. Commands: ValidatePortalSession, CheckEntitlement, IssueLaunchToken, ExpireLaunch. Events: LaunchTokenIssued {dealer_id, launch_token, issued_at, expires_at}, DealerEntitlementDenied {dealer_id, denial_reason, denied_at}."
    "F# Discriminated Union"
```

### Where the detail goes instead

| Detail type | Correct home |
|---|---|
| States, transitions | `domain.fs` F# Discriminated Union |
| Commands, Events, payloads | `domain.fs` + `.feature` file |
| Integration protocol details | Relationship technology field |
| Security risks, violations | DSL `properties {}` block + `tags "Committed Secret"` |

### Relationship labels

```dsl
// ✅ CORRECT — intent + protocol, ≤60 chars
accessGatewayApi -> entitlementStore "Reads entitlement config; appends events" "SQL"

// ❌ WRONG — narrating the implementation
accessGatewayApi -> entitlementStore 
    "Reads per-dealer entitlement configuration and appends the full LaunchSession event stream with dealer_id, issued_at, expires_at" 
    "Azure SQL"
```

**The diagram is a navigation map, not a data dictionary.** If a reader needs to know the event payload shape, they read `domain.fs`.

## 9. Docker / Tooling Setup

**Image notes:**
- `structurizr/cli` is **deprecated** — do not use it.
- Use `structurizr/structurizr:preview` — the consolidated image that merges CLI + Lite + on-premises.
- Only one service is needed for the visualization server. Validation is a **one-shot `docker compose run`** override, not a dedicated container.

**Standard docker-compose pattern:**

```yaml
services:
  structurizr:
    image: structurizr/structurizr:preview
    platform: linux/arm64      # required on Apple Silicon
    command: local             # runs Structurizr Lite web server
    ports:
      - "8080:8080"
    volumes:
      - ./core-model:/usr/local/structurizr

  structurizr-specs:
    image: structurizr/structurizr:preview
    platform: linux/arm64
    command: local
    ports:
      - "8081:8080"
    volumes:
      - ./specs-to-be:/usr/local/structurizr
    profiles:
      - specs                  # opt-in: docker compose --profile specs up

  structurizr-mcp:
    image: structurizr/mcp
    ports:
      - "3000:3000"
    command: ["-dsl", "-server-read", "-server-update", "-plantuml", "-mermaid"]
    depends_on:
      - structurizr
```

**Validation (Gate 1) — one-shot, no dedicated service:**
```bash
docker compose run --rm structurizr validate -workspace /usr/local/structurizr/workspace.dsl
```

**MCP config (`~/.copilot/mcp-config.json`):**
```json
"structurizr": {
  "command": "npx",
  "args": ["-y", "mcp-remote", "http://localhost:3000/mcp"]
}
```

**To start:**
```bash
docker compose up structurizr structurizr-mcp          # model-as-is + MCP
docker compose --profile specs up structurizr-specs    # specs overlay (opt-in)
```


Run `./scripts/0-ear-audit.sh` (or equivalent) before every commit. Typical gates:

| Gate | Check |
|------|-------|
| 1a | `structurizr-validate` on `model-as-is/workspace.dsl` |

## 12. `group` Blocks for Domain Organisation

Groups render a named boundary around elements. They work at every level of abstraction:

| Location | Groups can contain |
|----------|--------------------|
| `model` | People and softwareSystems |
| `softwareSystem` | Containers |
| `container` | Components |

Group membership does **not** affect identifier scoping under `!identifiers hierarchical` — members still use their normal names.

### Basic grouping (flat)

```dsl
model {
    group "Sales & E-Commerce" {
        magentoStorefront = softwareSystem "Magento" { ... }
        shopifyStore      = softwareSystem "Shopify" { ... }
    }

    group "Observability & Operations" {
        datadog = softwareSystem "Datadog" { ... }
    }
}
```

### Nested groups (domains + subdomains)

Nested groups require a `structurizr.groupSeparator` property on the `model` block. Without it, nesting is silently ignored.

```dsl
model {
    properties {
        "structurizr.groupSeparator" "/"
    }

    group "Commerce" {
        group "Sales" {
            pos = softwareSystem "Point of Sale" { ... }
        }
        group "Fulfilment" {
            wms = softwareSystem "Warehouse Management" { ... }
        }
    }

    group "Platform" {
        group "Identity" {
            iam = softwareSystem "IAM" { ... }
        }
    }
}
```

The separator is used to build the full hierarchical group name: `"Commerce/Sales"`, `"Commerce/Fulfilment"`, etc. **Do not use the separator character in group names themselves.**

### Styling groups

Style **all** groups with the reserved `Group` tag:

```dsl
styles {
    element "Group" {
        color #888888
    }
}
```

Style a **specific** group with `Group:<name>`:

```dsl
styles {
    element "Group:Commerce" {
        color #1168bd
    }
    element "Group:Platform" {
        color #2e8b57
    }
}
```

Style **nested** groups using the full separator-joined path:

```dsl
styles {
    element "Group:Commerce/Sales" {
        color #438dd5
    }
    element "Group:Commerce/Fulfilment" {
        color #85bbf0
    }
}
```

### Inline group assignment on components

Components can declare their group inline (alternative to wrapping in a `group {}` block):

```dsl
component "Order Validator" {
    group "Validation"
    technology "F# / Domain"
}
```

### Filtering views by group

Use the `element.group==` expression to include/exclude by group name:

```dsl
systemLandscape "L1_Commerce" {
    include "element.group==Commerce"
    autoLayout
}
```

## 13. Imperative Order — No Forward References

The DSL is **imperative**: elements must be defined before they are referenced. This fails:

```dsl
# BAD — b is referenced before it is defined
a = softwareSystem "A"
a -> b "Gets data from"          # ERROR: b does not exist

b = softwareSystem "B"
```

**Fix:** reorder definitions, or use the `this` keyword to write the relationship inside the destination element's block:

```dsl
!identifiers hierarchical

model {
    a = softwareSystem "A" {
        aa = container "AA"
    }

    b = softwareSystem "B" {
        bb = container "BB" {
            a.aa -> this "Sends data to"   # 'this' = bb; avoids forward ref
        }
    }
}
```

---

## 14. Always Specify Explicit View Keys

Auto-generated view keys are **not stable** — you will lose manual layout information when regenerating. Always provide an explicit key:

```dsl
# BAD — key is auto-generated and unstable
systemContext pim {
    include *
    autoLayout
}

# GOOD — key is stable and explicit
systemContext pim "L1_PIM_Context" {
    include *
    autoLayout
}
```

This aligns with the `L1_`/`L2_`/`L3_`/`DEP_` prefix convention (see section 5).

---

## 15. `!const` / `!var` for Shared Strings

Use `!const` (immutable) or `!var` (overridable) to DRY shared names like environment names, versions, or org labels:

```dsl
!const ORG "Silencer Central"
!const ENV_PROD "Production"

workspace "${ORG} Architecture" {
    model {
        deploymentEnvironment "${ENV_PROD}" { ... }
    }
}
```

Constants/variables support `${NAME}` substitution in any string token. Names: `a-zA-Z0-9-_.` only.

---

## 16. Relationship Uniqueness Constraint

All relationships between the **same source and destination** must have a **unique description**. Duplicate descriptions cause a parse error:

```dsl
# BAD — duplicate description between same pair
apiApp -> database "Reads from and writes to"
apiApp -> database "Reads from and writes to"   # ERROR

# GOOD — different descriptions are fine
apiApp -> database "Reads product data from"
apiApp -> database "Writes audit events to"
```

This also means you cannot create the same relationship twice across `!include`d fragments.

---

## 17. Tag Expressions in View `include`/`exclude`

When filtering elements in a view by tag, **quote expressions that contain whitespace**:

```dsl
systemLandscape "L1_Landscape" {
    include "element.tag==Existing Internal"   # CORRECT — quoted
    exclude "element.tag==Legacy"
    autoLayout
}
```

Without quotes, the DSL parser splits the expression at the space — a silent bug. Tag expressions:

| Pattern | Meaning |
|---------|---------|
| `element.tag==Tag` | elements with that tag |
| `element.tag!=Tag` | elements without that tag |
| `element.type==Container` | by C4 type |
| `relationship.tag==Tag` | relationship filter |
| `-><identifier>` | element + afferent couplings |
| `<identifier>->` | element + efferent couplings |

Combine with `&&` / `||`: `"element.type==Container && element.tag==Manager"`

## 18. `archetypes` for Ubiquitous Language

Define team-specific element types that extend the base C4 types. Reduces duplication and encodes the domain vocabulary:

```dsl
workspace {
    model {
        archetypes {
            # custom aliases for containers
            webApp    = container { technology "React / TypeScript"; tags "Frontend" }
            apiService = container { technology "Java / Spring Boot"; tags "Service" }
            dataStore  = container { technology "PostgreSQL"; tags "Database" }
        }

        mySystem = softwareSystem "My System" {
            ui  = webApp "Web Application" "Customer-facing UI"
            api = apiService "Core Service" "Business logic"
            db  = dataStore "Product Database" "Persistent storage"
        }
    }
}
```

Archetype defaults (technology, tags) can be overridden per-instance. Supported for: `person`, `softwareSystem`, `container`, `component`, `deploymentNode`, `infrastructureNode`, `group`, `element`.

---

## 19. `!impliedRelationships false` for Explicit Models

By default the DSL auto-creates implied relationships at parent levels (e.g., defining `person -> container` automatically implies `person -> softwareSystem`). For large EAR models, disable this to keep the model fully explicit:

```dsl
workspace {
    !impliedRelationships false

    model {
        u = person "User"
        s = softwareSystem "System" {
            app = container "Web App"
        }

        # Must now explicitly declare both levels
        u -> s "Uses"
        u -> app "Interacts with"
    }
}
```

## 21. Dynamic Views

Dynamic views show **ordered instances** of relationships to describe how a specific use case or feature works. They are scoped to a C4 level and use existing static-model relationships — you cannot add a relationship in a dynamic view that doesn't exist in the static model.

### Scope parameter determines element visibility

```
dynamic <*|softwareSystem|container> [key] [description] {
    ...
}
```

| Scope | Elements allowed in the view |
|-------|------------------------------|
| `*` | People + softwareSystems |
| `<softwareSystem>` | People, softwareSystems, containers |
| `<container>` | People, softwareSystems, containers, components |

### Basic syntax — enumerate relationships explicitly

Unlike static views, dynamic views do **not** support `include *` or `exclude`. You list each interaction in order:

```dsl
dynamic mySystem "L2D_Epic3_Checkout" "Checkout flow" {
    customer -> webApp "Submits order via"
    webApp -> orderService "Creates order in"
    orderService -> database "Persists order to"
    orderService -> emailService "Triggers confirmation via"
    autoLayout lr
}
```

You can **override the relationship description** to give it context-specific meaning (the underlying static description is unchanged):

```dsl
# Static model has: webapp -> database "Reads from and writes to"
# Dynamic view can re-label the same relationship:
webapp -> database "Queries for past orders"
```

### Explicit step ordering with `N:`

Use numbered prefixes when you want to control or repeat step numbers (e.g., parallel steps sharing the same number):

```dsl
dynamic mySystem "L2D_Epic3_Checkout" {
    1: customer -> webApp "Submits order"
    2: webApp -> orderService "Creates order"
    3: orderService -> database "Persists order"
    3: orderService -> emailService "Sends confirmation"   # same step = concurrent
    autoLayout
}
```

### Parallel sequences with `{...}` blocks

Use nested `{}` blocks to show concurrent branches:

```dsl
dynamic mySystem "L2D_Epic3_Checkout" {
    customer -> webApp "Submits order"
    webApp -> orderService "Creates order"
    {
        {
            orderService -> database "Persists order"
        }
        {
            orderService -> emailService "Sends confirmation"
        }
    }
    autoLayout
}
```

> **Tip:** Explicit `N:` ordering is more readable and less fragile than nested `{}` blocks for complex flows.

### Key naming convention

| Scope | Key pattern | Example |
|-------|-------------|---------|
| System scope (`L2D`) | `L2D_Epic{N}_{FeatureName}` | `L2D_Epic3_Checkout` |
| Container scope (`L3D`) | `L3D_Epic{N}_Feature{N}_{Name}` | `L3D_Epic3_Feature2_OrderCreate` |

### What dynamic views do NOT support

- `include` / `exclude` / `include *` — not permitted
- Tag expressions (`element.tag==...`) — not permitted
- Adding relationships that don't exist in the static model
- `autoLayout` direction is the only layout option (no manual layout for dynamic views)
